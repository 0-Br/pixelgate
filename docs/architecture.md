# pixelgate 架构

pixelgate 的系统设计与现行实现事实。

## 项目定位

pixelgate 是一个 stdio 传输的 MCP 服务，向 Claude Code 提供 `generate_image` 与 `edit_image` 两个工具。它把图像请求发给本机回环地址上的 CLIProxyAPI 网关，由网关用 ChatGPT 订阅的凭据转发到 GPT Image 后端。

能力边界：

- 只做单次、单图的生成与编辑，每次调用固定 `n=1`，不做批量、流式或变体。
- 只和一个网关通信，而且只通过 Images 的两个端点；不调用网关的管理接口，不拉起、不重启网关。
- 不持有任何上游凭据。它持有的只是网关的 client key，并且每次请求前现取。
- 客户端范围是 Claude Code，包括把模型请求转到同一网关的 Claude Code 会话。Codex 自带原生图像能力，不在支持范围内。

## 核心设计原则

- **出站只有一条路**：请求只能发往配置里的回环网关的两个 Images 端点。这由三道互相独立的约束共同保证：配置层只接受 `http://127.0.0.1:<端口>/v1`；传输层在建连前逐个核对 scheme、host、port 与路径；构造客户端期间临时摘掉 `OPENAI_*` 与代理环境变量（构造后放回），HTTP 客户端也不读环境里的代理设置。三道约束互相独立：配置层管配置写错，传输层管代码里拼错或被重定向的目标，环境清理管环境变量把请求引到别处，所以其中一处的实现缺陷由另外两道兜住。
- **每次调用都有可审计的落盘记录**：回执先以 `started` 写盘，再发请求，最后换成终态；所有文件排他创建，不覆盖。进程在任何一步被杀，留下的回执都能说明走到了哪一步，而上游是否已经生成、是否已经消耗额度，由 state 区分为 `failed` 与 `unknown`，不混为一谈。
- **不猜测、不补值**：回执里缺失的值写 null，不拿请求值冒充上游返回值；上游给出的尺寸与请求不同时照实记录 `size_mismatch`。
- **校验与 schema 同源**：两个工具的 inputSchema 与 outputSchema 直接由 pydantic 模型生成，校验器与对外声明的 schema 是同一份定义。错误类别、型号白名单与尺寸合法域都在 `schemas.py` 单点定义。
- **批准交给宿主**：服务自身不做任何权限判断，两个工具都声明 `_meta["anthropic/requiresUserInteraction"]=true`，由 Claude Code 每次调用前请用户批准。
- **不重试、不排队**：客户端 `max_retries=0`，不跟随重定向；同一进程已有调用在跑时，新调用立即返回 `busy`。重试与否由调用方在看到回执之后决定，因为每次请求都可能消耗额度。

## 技术栈

| 组件 | 选型与理由 |
| --- | --- |
| MCP 协议 | 官方 `mcp` SDK 的低层 `Server` 接口，stdio 传输 |
| 上游调用 | `openai` SDK 的 Images 接口，传输层换成自定义的 `httpx2.BaseTransport` 子类，以便在建连前做目标守卫与响应体量计数 |
| 数据模型与校验 | pydantic v2 |
| 图片解码与预览 | Pillow，只接受 png、jpeg、webp |
| 包管理与环境 | uv，`uv.lock` 锁定；运行依赖在 `pyproject.toml` 里钉死版本，因为 `uv tool install` 安装时不读锁文件 |
| 构建后端 | hatchling |
| 测试、lint 与类型检查 | pytest；ruff（配置自足）；basedpyright，standard 档，带基线 |

不选的：没有另外的选型记录；现行实现用的是 `mcp` 的低层 `Server` 接口而不是高层封装，工具清单与返回内容逐字段手工组装；HTTP 调用走同步客户端，放在工作线程里执行。

## 模块

| 模块 | 职责 |
| --- | --- |
| `schemas.py` | 配置、请求与回执的数据模型；错误类别与告警类别枚举；型号、尺寸、质量、背景四类参数的合法域与校验函数 |
| `client.py` | 读配置、调用 helper 取 client key、目标守卫传输、构造 SDK 客户端，以及生成与编辑两条调用的完整流程（预检、写 started 回执、发请求、解码、落盘、写终态回执） |
| `artifacts.py` | 输入图快照与校验、mask 核对、产物目录的排他创建、文件排他写、上游图片的解码验真与预览生成 |
| `server.py` | MCP 工具定义、调用结果的组装、进程内并发锁、命令行入口（`--config` 与 `check-config` 子命令） |

依赖方向是 `server` → `client` → `artifacts` → `schemas`，`schemas` 不依赖其他模块。

## 调用流程与 state

一次调用依次经过：参数校验（形态错误即 `request_invalid`，不建目录）；输入图快照与校验（失败即对应的 `input_*` 类别，不建目录）；排他创建产物目录并写入输入快照、`prompt.txt`、`request.json`；以 `started` 写回执；调用 helper 取 key 并发出请求；读取并解码响应；写 `image.png` 与 `preview.jpg`；以终态重写回执。

回执的 state 只在两处从 `started` 换成终态：成功路径写 `completed`，失败路径按「请求是否已经发出」写 `failed` 或 `unknown`。请求没有发出（本地预检失败、helper 失败、建连失败）一律 `failed`；请求已经发出而没能拿到完整结果（连接中断、超时、写盘前中断）一律 `unknown`，因为上游可能已经生成并消耗了额度。回执是唯一允许被替换的文件，并且只允许从 `started` 换成终态。

## 并发与取消

两个工具的实现是阻塞的，单次最长可达 600 秒以上，所以调用跑在工作线程里，事件循环只处理协议帧；否则第二个调用连请求都进不来，`busy` 也就无从返回。锁是进程级的，不跨进程。

本版没有取消通道：宿主取消调用时，服务等工作线程跑完，产物与终态回执照常写盘，只是宿主收不到返回。

## 输出约束

stdout 只承载 MCP 协议帧；日志写 stderr，不含 prompt、图片内容、上游原文与凭据。返回给宿主的预览是 JPEG，按 100 KB 的 base64 预算缩放，超预算时省略图像块并记告警，因为过大的图像块会挤占宿主的上下文。
